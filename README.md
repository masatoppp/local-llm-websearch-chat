# ローカルLLMを活用したWeb検索チャット

Qwen3をローカル環境で動作させ、TavilyによるWeb検索、会話履歴、Reflection（回答評価・再生成）を組み合わせたチャットシステムです。

自分のPC上でローカルLLMを動作させ、モデルの事前知識だけで回答する場合と、Web検索による最新情報を組み合わせる場合を制御することを目的に構築しました。

すべての質問でWeb検索を実行するのではなく、質問内容から検索の必要性を判定し、必要な場合のみWeb情報を取得します。

また、プロンプトによる制御だけでは誤生成を完全には防げないため、回答生成後に別モデルによるReflectionを行い、問題が検出された場合のみ再生成する構成としています。

## 主な機能

- Qwen3によるローカルLLMでの回答生成
- 質問内容に応じたWeb検索要否の判定
- Tavilyを利用したWeb検索
- 「今日」「昨日」「明日」などの相対日付を具体的な日付へ変換
- 会話履歴を利用した継続的な対話
- 別モデルによるReflection（回答評価）
- Reflectionで問題を検出した場合の回答再生成
- 各処理および全体の処理時間計測

## モデル構成

処理内容に応じて2つのQwen3モデルを使い分けています。

### Qwen/Qwen3-1.7B

- Web検索要否判定
- 初回回答生成

比較的単純な処理には軽量モデルを使用し、ローカル環境での処理負荷を抑えています。

### Qwen/Qwen3-4B

- Reflection
- ReflectionがFAILとなった場合の回答再生成

回答品質の評価では誤判定をできるだけ減らしたいため、初回生成より大きなモデルを使用しています。

両モデルとも4bit量子化し、手元のGPU環境で実行できる範囲に収めています。

## 処理フロー

```text
ユーザー入力
    ↓
相対日付の変換
    ↓
Qwen3-1.7BでWeb検索要否を判定
    ├─ 検索不要
    │      ↓
    │  Qwen3-1.7Bで回答生成
    │
    └─ 検索必要
           ↓
       Tavily検索
           ↓
       Qwen3-1.7Bで回答生成
           ↓
     Qwen3-4BでReflection
        ├─ PASS
        │    ↓
        │  最終回答
        │
        └─ FAIL
             ↓
        Qwen3-4Bで再生成
             ↓
           最終回答
             ↓
        会話履歴へ保存
```

Reflectionは繰り返しループさせず、初回回答に対して1回実行します。

FAILの場合も再生成は1回のみとし、ローカルLLMで複数回生成することによる処理時間増加とのバランスを取っています。

## Web検索

Web検索にはTavily APIを使用しています。

最新情報を取得できることに加え、検索件数などをパラメータで調整しやすいため採用しました。

例えば、

- 一般的なPythonの文法や用語 → ローカルLLMのみ
- 今日のニュースや明日の天気 → Web検索を実行

というように、最新の外部情報が必要かどうかによって処理を分岐させています。

取得した検索結果からタイトル、URL、本文を整形し、回答生成用LLMのコンテキストとして渡します。

## 会話履歴

ユーザーとAIのやり取りをリスト形式で保持し、次の回答生成時にも利用します。

会話履歴を保持することでモデル自体の知識を増やすのではなく、前の質問・回答の文脈を引き継ぎ、省略された表現や継続質問を解釈しやすくすることを目的としています。

## Reflection

初回回答をQwen3-4Bへ渡し、主に以下の観点から評価します。

- ユーザーの質問に回答できているか
- Web検索結果と矛盾していないか
- 検索結果に存在しない情報を追加していないか
- プログラミング上の明らかな誤りがないか
- 存在しないAPIやメソッドを生成していないか
- 会話履歴と無関係な内容が混入していないか
- 日付情報と回答内容が整合しているか

判定結果は `PASS` または `FAIL` とし、`FAIL` の場合だけQwen3-4Bで回答を再生成します。

現状ではReflectionの評価結果そのものを詳細な修正指示として再生成へ渡すのではなく、`PASS / FAIL` を再生成の判定に利用しています。

## 動作検証で確認した課題

検証では、一連の処理が動作することを確認する一方で、いくつかの課題も確認しました。

検索不要と考えられる一般知識の質問でも、小型LLMによるWeb検索要否判定が誤る場合があります。

また、Web検索を実行しても、取得された検索結果の内容や順位によって最終回答の品質が左右されるため、Web検索そのものが回答の正確性を保証するわけではありません。

Reflectionについても、追加の品質確認工程としては有効ですが、誤生成を完全に防止できるものではありません。

さらに、ローカル環境では初回生成、Reflection、再生成と複数回モデルを動作させるため、FAIL時には処理時間が大きくなることも確認しました。

## 今後の改善案

- Web検索要否判定をLLMだけでなくルールベースと組み合わせる
- Web検索結果の情報源や関連度を評価してから回答生成へ渡す
- Reflectionで `PASS / FAIL` だけでなく、問題点や修正理由も生成して再生成へ渡す
- 長い会話履歴をすべて保持せず、要約や必要部分の抽出を行う
- モデルサイズや生成Token数を調整し、品質と処理時間を比較する
